## 今日完成

最终确定的选题是：

> **Hermes 高质量协作方法：我如何用上下文、任务与验收构建可复用工作流**

目标读者是已经掌握 Hermes 基础使用，希望进一步复用自动化工作流的中文进阶用户。内容采用个人实践复盘的形式，以 HermesCN 自动打卡作为主案例，以学习文档维护作为辅助案例。

> **怎样把一个自动化想法定义成 Agent 能持续执行、人在关键节点保留决定权、最终结果又能够被检查的任务？**

## 核心洞察

我原本拥有不少关于 Hermes 的学习材料，但“材料多”不等于“创作方向清楚”。如果不先限定读者和问题，很容易再次写成一篇大而全的功能说明。

经过梳理，我确认自己真正可以贡献的不是对 Hermes 功能的转述，而是三个来自实际协作过程的方法：

1. **上下文分层**  
   稳定偏好、可复用流程、项目规则和本次任务应分别管理，而不是全部塞进一条 Prompt。

2. **任务结构化**  
   在执行前明确背景、目标、输入、限制、交付物和验收标准，降低需求歧义、遗漏和任务漂移。

3. **结果可验证**  
   工具调用成功不等于任务完成。外部写入需要回读确认，文档修改也要检查结构、索引和链接，最终结论必须有真实证据支撑。

这让我进一步认识到：高质量使用 Hermes 的重点，不是把指令写得越来越长，而是把任务转化为一份清楚的协作契约。

# 2026-09-11

# Day 2｜让 Hermes 反驳我，而不是只认同我

今天围绕 Day 1 确定的创作方向，继续检验文章的核心判断：

> **Hermes 协作质量的关键，不是把 Prompt 写得更长，而是把上下文、任务边界和验收证据组织清楚。**

这次没有直接让 Hermes 扩写观点，而是要求它提出有依据的反对意见，检查这句话是否说得过满、证据是否充分，以及它适用于哪些任务。

## 今日完成

我先结合已有的自动打卡实践，向 Hermes 说明自己的初步看法：

- 自动化任务需要明确输入、权限和执行边界；
- 外部写入不能以接口返回成功作为最终完成依据；
- 长期偏好、可复用流程、项目规则和当前任务应分层管理；
- 一份结构化任务卡有助于减少遗漏和任务漂移。

Hermes 随后从四个方向提出质疑：

1. **任务结构不是唯一决定因素**  
   如果模型能力不足、工具不可用或外部接口存在缺陷，任务描述再清楚也无法保证成功。

2. **单个案例不能证明因果**  
   自动打卡流程可以说明这套方法能够落地，但不能证明任务成功主要由上下文分层和验收机制带来。

3. **完整任务卡并非适用于所有任务**  
   对一次性、低风险、容易撤销的小任务，填写完整任务卡可能带来不必要的沟通成本。

4. **上下文分层本身也可能产生问题**  
   如果 Memory、Skill 或项目规则已经过期、相互冲突或被错误加载，它们也可能成为新的任务漂移来源。

## 我如何处理这些疑问

我没有因为这些质疑而放弃原判断，因为上下文、任务结构和验收标准仍然是用户能够直接控制的重要变量。

但我接受了“关键不等于唯一”的反对意见，并对原判断进行了三项修正。

### 第一，降低结论强度

原来的判断容易让人理解为：只要任务结构清楚，Hermes 就一定能产生高质量结果。

现在修改为：

> **对于多步骤、需要复用或涉及外部写入的 Hermes 任务，上下文分层、任务结构和结果验收是影响协作质量的关键可控因素，但不是唯一决定因素；模型能力、工具可用性和外部系统状态也会独立影响结果。**

### 第二，增加适用边界

这套方法重点适用于：

- 包含多个执行阶段的任务；
- 需要跨会话持续推进的任务；
- 准备沉淀为 Skill 或自动化流程的重复任务；
- 涉及 API、文件修改、内容发布等外部写入的任务；
- 需要提供明确验收证据的任务。

对于简单、低风险、结果直观且容易撤销的任务，不一定需要完整填写任务卡，可以只说明目标、交付物和完成条件。

### 第三，降低案例的证明强度

自动打卡将继续作为文章的主案例，因为它能够清楚展示：

> 真实材料 → 只读检查 → 草稿生成 → 人工终审 → 幂等提交 → 回读验证

但它只是一项说明性案例，可以证明方法如何落地，不能单独证明这套方法是成功的唯一原因。

文章中不会再把个人经验直接包装成普遍规律，而会明确区分：

- 已经发生的事实；
- 从案例中得到的解释；
- 仍然需要验证的假设。

## 核心理解

今天最重要的学习不是得到一个更坚定的观点，而是理解了一个判断至少需要检查四个方面：

1. **理由是否支持结论；**
2. **证据是否足以支撑当前的表达强度；**
3. **是否存在其他合理解释；**
4. **结论在什么条件下成立，又在什么条件下可能失效。**

Hermes 提出的反对意见没有直接推翻我的观点，而是帮助我发现原判断缺少适用范围、替代解释和证据等级。

这让我认识到，与 Hermes 讨论时，不能只让它继续补充支持材料。更有价值的方式是主动要求它寻找反例、追问隐藏假设，并说明什么证据可能改变当前判断。

## 今日产出与待验证问题

今天完成了一张个人思考卡和一段关键讨论记录，明确记录了：

- 最初判断；
- 支持理由；
- 隐含假设；
- Hermes 提出的反对意见；
- 自己决定保留、修改或暂缓的部分；
- 能够改变当前判断的条件。

目前保留以下待验证问题：

1. 同一任务分别使用模糊指令和结构化任务卡时，结果完整性与返工次数有何差异？
2. 哪些失败来自任务描述，哪些来自模型能力、工具权限或外部接口？
3. 从什么复杂度开始，完整任务卡的收益会超过填写成本？
4. 如何发现 Memory、Skill 和项目规则已经过期或彼此冲突？
5. 自动打卡方法能否稳定迁移到资料整理、内容发布等其他工作流？

通过实际对照，为文章的核心判断补充证据，而不是继续依赖直觉或单个成功案例。

# 2026-09-12

## Day 3｜与 Hermes 一起研究和验证观点

今天的重点不是继续为原有观点寻找支持，而是检查：**哪些材料真正支持我的判断，哪些材料只与它方向一致，哪些材料反而要求我降低结论强度。**

在 Day 2 中，我已经把最初的判断修正为：对于多步骤、需要复用或涉及外部写入的 Hermes 任务，上下文分层、任务结构和结果验收是重要的可控因素，但不是唯一决定因素。今天进一步通过官方文档、厂商技术资料、协议规范和个人实践记录，对这句话进行了来源核验。

### 今日完成

我将已有材料分成了四类：

1. **原始材料**  
   包括 Hermes 官方文档、目标系统的接口契约、协议规范和厂商的一手技术资料。这些材料可以支持它们明确记载的机制和事实。

2. **个人实践证据**  
   包括自动打卡的真实执行与回读记录，以及曾经错误复用历史主题、重新读取当天材料后完成修正的经历。它们可以证明“我做过什么、遇到过什么问题”，但不能直接证明普遍规律。

3. **转述和二手归纳**  
   社区案例总结可以帮助发现线索和寻找案例，但不能因为某种方法经常出现，就把它当成已经验证的性能结论。

4. **尚无法核实的判断**  
   例如“结构化任务卡能够降低返工”“同一套分层方法能迁移到所有工作流”，目前还缺少对照实践，只能保留为待验证假设。

研究过程中，我也实际区分了 Hermes 的两种网页工具：

- `web_search` 适合发现候选来源和获得排序结果；
- `web_extract` 适合读取网页正文，但长页面可能被截断，JavaScript 较重的页面也可能提取不到有效内容。

本次部分网页提取返回空内容。我没有把空结果解释为“网页没有资料”，而是改用其他读取方式打开页面，并核对关键原文。这让我更明确地认识到：

> **搜索结果只是线索，提取结果也不是最终证据；重要结论必须回到原始来源。**

### 核心发现

#### 1. 上下文需要精选，但具体分层不是唯一标准

外部资料支持的核心原则是：上下文是一种有限资源，应尽量选择与当前任务相关的高信号信息，而不是不断向 Prompt 中堆叠背景。

这与我使用 Memory、Skill、项目规则和当前任务进行分层的做法方向一致，但原始资料并没有证明 Hermes 的这套具体分层是唯一正确答案。

因此，我决定把它写成：

> **外部资料支持“精选上下文”；Memory、Skill、项目规则和当前任务的分层，是我结合 Hermes 机制形成的个人实现方法。**

这个修改避免了把个人实践包装成官方标准。

#### 2. 任务结构的作用是减少歧义，不是增加字段

Agent 评估资料通常将任务定义为具有明确输入和成功标准的测试。Hermes 的 Completion Contract 也提供了：

- `outcome`
- `verification`
- `constraints`
- `boundaries`
- `stop_when`

但这些字段是可选的，并不意味着每一个任务都必须填写完整合同。

因此，结构化任务卡的价值不应被描述为“写得越详细越好”，而应该是：

> **只补充那些能够消除关键歧义、划清范围或定义完成条件的信息。**

对于一次性、低风险、容易撤销的小任务，只说明目标、交付物和完成条件可能已经足够。只有在任务跨越多个步骤、多个会话或外部系统时，完整结构的收益才可能超过成本。

#### 3. 最终状态验证获得了最强支持

多份资料都明确区分了 Agent 的执行记录和环境中的最终结果。

Agent 说“已经完成”、工具返回成功、命令退出码为零，都只是过程证据。真正的完成状态取决于：

- 目标文件是否真的存在；
- 测试是否真实通过；
- 外部记录是否已经创建；
- 正文和关键字段是否符合预期；
- 已声明的验收条件是否逐项成立。

这直接支持了我原来的一个判断：

> **工具调用成功不等于业务结果正确，动作获准也不等于结果通过验收。**

但今天也补充了一项重要边界：回读并不是无条件可靠。不同系统可能采用强一致或最终一致模型，列表查询有时可能暂时读到旧数据。因此，回读时应尽量使用返回的资源 ID 或精确对象接口，并理解目标系统的一致性语义。

#### 4. 人工确认、幂等和回读不能互相替代

以前我容易把“人工确认—幂等提交—GET 回读”整体描述为一个安全闭环。今天进一步确认，这些机制分别解决不同问题：

- **人工确认**：控制是否允许执行公开、敏感、不可逆或高风险动作；
- **幂等键**：控制网络超时或结果不确定时的重复提交风险；
- **写后回读**：检查外部系统当前是否呈现预期状态；
- **条件写入或版本校验**：防止多个客户端同时修改时发生覆盖。

人工确认不能证明执行成功，幂等键不能证明正文正确，回读也不能解决并发覆盖。它们需要根据任务风险和目标系统能力组合使用，而不是把任何一项当成完整保证。

### 观点发生了什么变化

经过核验，我没有推翻文章的创作方向，但进一步降低了结论强度。

原来的表达接近：

> 上下文分层、任务结构和结果验收是 Hermes 高质量协作的三个关键。

现在修改为：

> **对于多步骤、需要复用或涉及外部写入的 Hermes 任务，精选上下文、明确任务和验证最终状态，是三项重要的可控设计。它们能够减少歧义、暴露失败并限制风险，但目前还不能证明它们必然降低返工，也不能排除模型能力、工具设计和外部系统状态的影响。**

其中：

- “精选上下文”有外部原则支持；
- Hermes 的具体分层属于个人实现方法；
- “明确任务”有助于定义输入、边界和成功标准；
- “结果验收”获得的直接支持最强；
- “降低返工”和“适用于所有工作流”仍然只是待验证假设。

### 今日产出

今天完成了一份带来源的素材清单，并为每项材料记录了：

- 来源属于原始材料、个人记录、转述还是无法核实内容；
- 它支持、冲突或限定了什么观点；
- 可以安全写入什么结论；
- 不能从中推出什么结论。

同时确认了文章的五部分结构：

1. 从一次“写得合理却不真实”的失败切入；
2. 说明个人记录、接口契约和外部资料的证据边界；
3. 解释精选上下文、明确任务和验证结果三项可控设计；
4. 用自动打卡和文档维护两个案例说明方法如何落地；
5. 提供一张最小任务卡，并公开仍待验证的问题。

今天还纠正了一个执行边界问题：研究过程中产生的中间材料不应散落在用户根目录，而应统一保存在项目工作区。这个修正提醒我，工作流质量不仅包括内容是否正确，也包括产物位置和任务范围是否得到遵守。

### 明日计划

下一步不再继续搜集支持相同观点的文章，而是补充目前最缺少的行为证据。

我准备选择一个输入固定、结果可核对、能够重复执行的小任务，分别使用：

- 简短自然语言指令；
- 结构化任务卡。

在尽量固定模型、工具、输入和运行环境的情况下，对两种方式各执行多次，并记录：

- 关键遗漏数量；
- 人工纠正次数；
- 最终验收是否通过；
- 额外沟通和执行成本。

如果结构化版本没有稳定改善结果，就继续降低文章结论的强度；如果它只在复杂或高风险任务中有效，就进一步缩小适用范围。

- 希望读者解决什么问题；

- 哪些内容属于个人实践；
- 哪些结论已有外部资料支持；
- 哪些效果仍然缺少证据；
- 全文应采用什么结构和表达方式。

确认理解一致后，Hermes 按五部分结构完成初稿：

1. 从一次“写得合理却不真实”的打卡草稿切入；
2. 解释个人记录、接口契约、厂商资料和社区案例各自能证明什么；
3. 展开精选上下文、明确任务和验证最终状态三项设计；
4. 用自动打卡和文档维护说明方法如何落地；
5. 提供最小任务卡，并保留尚待验证的问题。

起草过程中没有把缺少依据的内容补写成事实。文章明确保留了三个待验证问题：

- 结构化任务卡是否能够稳定降低返工；
- 从什么复杂度开始，完整任务卡的收益会超过沟通成本；
- 当前的上下文分层能否迁移到更多工作流。

### 人工反馈与修改

初稿完成后，我按事实准确性、表达清晰度和个人语气逐段检查。第一次阅读时，我对三个部分的总体判断都是“基本 OK”，但这种反馈无法直接指导修改。

Hermes 随后把总体评价转化为三个具体的编辑取舍，我逐项作出决定：

1. **压缩开头，把核心判断提前。**  
   初稿用了三段才从错误案例落到方法。修改稿将其压缩为两段，第一段直接指出问题来自取证顺序，而不是文笔；第二段提前提出“写作前先建立事实清单”的判断。

2. **减少协议术语，保留机制分工。**  
   初稿在解释外部写入时使用了较多协议术语，容易让文章偏向接口教程。修改稿删除了不必要的术语，重点说明人工确认、幂等提交和写后回读分别解决什么问题，以及它们为什么不能互相替代。

3. **增加一张填写完成的任务卡。**  
   初稿只有抽象模板，读者仍需自己推断每个字段如何使用。修改稿增加了自动打卡示例，具体展示背景、目标、输入、限制、交付物、验收和复用方式。

这三次修改没有改变文章的核心判断，而是调整了信息顺序、解释层级和读者可操作性。

### 核心理解

今天最重要的认识是：让 Hermes 执行内容创作，不等于把材料一次性交给它，然后接受一篇看起来完整的文章。

真正的协作至少包含四次判断：

```text
确认任务理解
→ 生成可审阅初稿
→ 人决定事实、边界和表达取舍
→ Hermes 根据具体反馈修改
```

其中，人的作用不是在最后简单回复“可以”，而是决定：

- 哪个判断应该提前；
- 哪些技术细节会增加读者负担；
- 哪些结论说得过强；
- 哪个案例最能帮助读者理解；
- 文章应该停留在方法解释，还是继续提供可执行模板。

今天也实际运用了清晰表达的几个原则：首段尽早提出核心判断，每段只处理一个中心问题，一句话尽量只表达一个判断，并删除不能帮助读者行动的术语。对这篇文章来说，清晰不只是缩短句子，更重要的是按照读者的理解顺序组织内容：

```text
先看到真实问题
→ 再理解证据边界
→ 然后学习方法
→ 通过案例观察方法
→ 最后拿到可以直接使用的任务卡
```

修改稿保留了五部分主体结构，同时加入了一张填写完成的自动打卡任务卡。文章中的外部资料引用已通过证据检查，项目文档的标题、代码块和本地链接也完成了检查。

现在的文章能够支持一个较为克制的结论：

> 对于多步骤、需要复用或涉及外部写入的 Hermes 任务，精选上下文、明确任务和验证最终状态，是三项重要的可控设计。它们能减少歧义、暴露失败并限制风险，但目前还不能证明它们必然降低返工。

# 2026-09-14

# Day 5｜与 Hermes 一起编辑，并保存创作方法

今天完成的不是一次普通润色，而是把前四天形成的文章和协作过程同时变成可审核、可复用的资产。

## 一、先审核问题，不直接重写正文

我先让 Hermes 按事实、来源、论证和表达四个维度检查修改稿，并要求它只输出具体问题，不直接改写全文。

审核后的判断是：文章的核心框架基本成立，但还不能直接发布。主要问题包括：

1. 文章提到 Day 1—Day 3 的自动打卡已经提交并回读，但项目材料里没有保存逐次、脱敏且可核对的外部执行证据。独立审核因此一度把“证据在项目中不可见”误判成“Day 3 没有提交”。
2. “这些设计能减少歧义、暴露失败并限制风险”的因果强度仍然偏高。现有材料只能说明它们在当前案例中帮助我发现问题，不能证明它们在所有工作流中都会产生同样效果。
3. “固定幂等键”容易被理解成不同任务长期共用同一个键。更准确的说法是：为一次逻辑操作确定幂等键；当结果不确定时，使用相同方法、路径、正文和原键重试。
4. 部分引用只能支持前半句，后半句其实是我的风险判断。例如，外部资料支持高风险或不可逆动作需要人工监督，但不能直接推出所有低风险写入都不需要审批。
5. 一项特定产品的一致性说明被写成了所有目标系统都适用的结论，需要改回具体例证。
6. 验收部分仍然包含较多协议术语，容易让文章从“协作方法”偏成接口安全教程。
7. 自动打卡任务卡虽然提到了幂等提交，但没有把重试条件明确写进限制或验收字段。

我决定采纳全部高、中优先级修改，再让 Hermes 形成定稿，而不是让它自行判断哪些问题可以忽略。

## 二、完成定稿，并补齐项目内的证据链

针对审核结果，我和 Hermes 完成了以下修正：

- 将核心判断收紧为：在当前案例中，精选上下文、明确任务和验证最终状态帮助我更早发现歧义与失败，并有助于缩小风险暴露范围；它们不是成功的唯一原因，也不能据此证明必然降低返工。
- 重新只读查询目标系统，确认 Day 1—Day 4 四条打卡记录仍然存在。
- 将日期、Check-in ID、创建时间、项目匹配和正文一致性结果整理为脱敏证据，使后续审核不再依赖当前会话或口头总结。
- 把幂等规则改成针对一次逻辑操作的重试约束，避免“所有请求共用固定键”的歧义。
- 将人工确认、幂等提交和写后回读的职责分开表达，不再让某一个机制承担全部安全结论。
- 把特定系统的一致性行为明确写成例证，并说明没有证据表明自动打卡接口存在同样行为。
- 压缩并发控制和一致性相关术语，只保留会影响读者判断的机制边界。
- 在填写完成的自动打卡任务卡中补入幂等重试条件。

定稿引用检查通过：正文使用了 11 个来源，引用覆盖率为 38%。这个数字表示可由外部来源支持的陈述得到了核对，并不意味着个人经验也应由外部资料替代。

## 三、把创作方法保存为聚焦的 Skill

我没有创建一个“万能写作 Skill”，而是把范围限定为：证据驱动的个人实践复盘写作。

Skill 保存的不是这篇文章的标题、案例和结论，而是一套可以跨选题执行的步骤：

1. 先读取当前 Session、项目材料、执行记录和外部状态；
2. 明确读者、核心问题、非范围、交付物和验收条件；
3. 区分个人执行记录、目标系统契约、第一方资料、二手转述和未验证解释；
4. 为每项证据记录“能支持什么”和“不能推出什么”；
5. 用反对意见、替代解释和适用边界检查核心判断；
6. 确认提纲和证据边界后再起草；
7. 缺少依据时明确标记，不补造经历、数据或因果效果；
8. 保留初稿，收集位置明确的人工反馈；
9. 先输出审核问题，由人决定哪些修改需要采纳；
10. 修改后检查引用、结构、本地链接、篇幅和项目路径。

信息的保存边界也进一步明确：长期写作偏好进入记忆；可重复的创作步骤进入 Skill；单篇文章的标题、案例、来源、稿件版本和进度只留在项目材料中；凭据、临时路径和一次性调试信息不进入长期记忆。

## 四、使用新选题进行真实测试

为了避免只用原文章验证原方法，我选择了一个不同的小任务：为什么“研究内容正确，但文件写到错误目录”仍然属于任务失败？

这个测试要求 Hermes 在没有原对话帮助的情况下读取已有证据，区分错误发生时的历史记录与当前状态，不把一次路径错误泛化成所有子 Agent 的共同问题，保留无法证明的部分，并给出可以实际执行的路径检查。

测试文章最终正文为 639 个汉字，符合 600—900 字的要求；结构、证据边界和路径约束检查通过。它明确区分了迁移时的文件数量和当前文件数量，也没有把一次实践写成普遍因果。

第一版 Skill 被判定为“有条件通过”，因为真实测试暴露了三个缺口：

1. 隔离式一次性交付无法取得成稿后人工反馈时，没有规定应该如何降级；
2. “中文 600—900 字”没有确定性的计数口径；
3. “检查是否包含凭据”没有说明具体扫描方式及其能力边界。

因此，我没有把缺失的人工反馈伪造成已经完成，而是明确记录该环节不可用，只允许根据事先确认的验收标准进行确定性修正。

随后，Skill 增加了无反馈时的降级路径、中文正文长度的默认统计口径，以及凭据扫描只能覆盖常见模式的限制说明。再次回读时，还发现“允许无反馈降级”与最终通过条件仍有冲突，因此继续修正为 v0.1.2，明确区分人工决定、Hermes 建议和确定性修正。

## 五、今天形成的判断

今天最重要的收获是：保存创作方法，不是把这次写作过程原样复制进 Skill，而是识别其中跨任务仍然成立的步骤，再用一个不同任务暴露隐含前提。

目前可以确认：

- 文章已经完成事实、来源、论证和表达审核，并形成定稿；
- 创作流程已经被整理成范围明确的 Skill；
- Skill 的核心证据写作能力通过了一次独立任务测试；
- 测试确实发现了原流程没有覆盖的问题，并推动了两轮修正。

目前还不能确认：

- 这个 Skill 已经适用于所有技术文章或内容类型；
- 一次独立测试足以证明流程长期稳定；
- v0.1.2 已经完全消除了所有跨会话问题；
- 结构化任务卡必然降低返工；

Day 7 仍需要用另一个新选题重新运行精简流程，检查 v0.1.2 是否能够主动完成关键步骤，以及我是否还需要反复补充相同要求。
