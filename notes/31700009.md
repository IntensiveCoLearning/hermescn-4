# 2026-09-10

HermesCN 残酷共学第三期｜Day 1 打卡

今日创作任务卡

<br />

暂定标题

同名用户说话，AI 却认错人：我如何用 Codex 定位并修复 Hermes Agent 的飞书共享会话身份丢失问题

<br />

目标读者

正在使用 Hermes Agent 接入飞书群聊的开发者；希望理解 Agent 如何协助真实开源修复的人；对 FDE 式“从用户问题到可验证交付”感兴趣的人。

<br />

核心问题

在飞书群共享会话中，不同用户可能使用相同的 display name。Hermes 保留了群内共享上下文，但进入 Agent 的消息只显示名字、不含稳定的 sender ID，因此模型可能认错人。简单开启 group\_sessions\_per\_user 虽然能区分用户，却会拆散群共享上下文，不符合实际协作场景。

<br />

内容形式

一篇带代码差异、测试证据和反思的技术复盘，重点呈现真实诊断过程，而不只贴最终代码。

<br />

已有一手材料

真实飞书群使用问题；Codex 完整修复会话；Hermes Agent 源码和 Gateway 测试；PR #107120；Commit e586a1bc。

<br />

今天完成的工作

<br />

1．澄清问题边界

Codex 的第一版沿着“不同用户进入不同 session”的方向，尝试把 sender ID 加进 session key。进一步核对后发现，这会破坏群聊共享上下文。真正需要的是：共享同一个群 session，但每条进入 Agent 的消息都保留稳定的发送者身份。

<br />

2．完成最小可复用修复

在 Base Gateway 增加可扩展的 sender identity hook；Feishu Adapter 返回 sender\_id；共享群 session 的入站消息附带身份前缀；私聊不添加前缀；缺少 sender ID 时保持兼容。这样同名用户仍可被稳定区分，同时继续共享群聊上下文。

<br />

3．用测试锁定边界

新增测试覆盖：群聊消息包含稳定 sender ID；同名不同 ID 可区分；两人仍共享同一个 group session key；私聊不注入前缀；没有 identity 时维持原行为。

<br />

测试证据：第一版修改前为 4 failed、4 passed；修改后为 8 passed；纠正成“共享 session 加消息身份前缀”后，相关测试为 11 passed。完整 gateway 测试曾为 77 passed、1 failed，失败项是并发去重测试；单独重跑通过，因此如实记为疑似既有 flaky 行为，而不宣称整套测试全绿。ruff check、git diff check 和兼容性检查通过。

<br />

4．提交上游 PR

分支：fix/feishu-shared-sender-attribution

<br />

今天最重要的反思

这次最有价值的不是让 Codex 快速写出补丁，而是纠正了一个看似合理、实则破坏产品语义的方案：“身份归属”不一定应该进入“会话分区”。

<br />

群聊 session key 表达共享对话空间；sender ID 表达每条消息的来源。两者是不同维度。使用 Coding Agent 处理真实问题时，我仍需负责：明确不可破坏的产品语义；检查局部修复是否改变系统边界；用失败测试、回归测试和异常说明形成可审查证据。

<br />

七天预期成果

完成一篇可公开发布的技术复盘，呈现以下链路：真实群聊问题 → 错误的第一假设 → 代码路径定位 → 方案纠偏 → 最小实现 → 测试与 flaky 识别 → 上游 PR → 对 AI 协作开发的反思。

<br />

# 2026-09-11

HermesCN 残酷共学第三期｜Day 2 打卡

今天我突然想通了一件事：我之前的文案 AI 味太重，可能不只是文案写得不好，而是整个顺序错了。

我原来的做法接近于：先让 AI 生成一份完整逐字稿，我再对着它录。这样录的时候，我一直在注意自己有没有念错、有没有漏字。哪怕文案内容没问题，说出来还是很像朗读，不像我真的在跟人讲一件自己想明白的事情。

今天我试着把顺序倒过来。

先不要让 AI 写逐字稿。我直接对着录音断断续续地说，把想到的观点、例子、犹豫和重复都说出来。这一遍不追求能发布，只是把我脑子里真实存在的东西倒出来。

然后把语音转成文字，交给 Hermes。它不负责把文字润色成一篇可以照念的稿子，而是帮我找到主线：我的核心判断是什么，前后因果怎么连接，哪些地方重复了，哪里缺了一个例子，哪里其实还只是一个假设。

今天 Default Profile 里的真实对话也是这样。我先零散口述了一段“额度焦虑会限制人探索 AI 边界”的观点。Hermes 把它整理成了“额度焦虑 → 不敢尝试 → 错过 Aha Moment；额度充裕 → 放开尝试 → 发现新能力 → 联想到更多任务”。

我随后提出，不要再给我完整文案，只要给我更详细的思路大纲，我看着大纲自己完成整段论述。第一版大纲出来后，我又觉得逻辑节点太少，要求继续加密。这个过程让我意识到，我真正需要的不是几个关键词，也不是一篇逐字稿，而是一张“论述路标”。

它应该细到让我知道下一段要回答什么、用哪个例子、怎么接到后面；但不能细到把每一句话都替我写好。具体怎么找词、哪里停顿、临时补一句什么，仍然由我在录制现场决定。

正式录制时，也不必追求一镜到底。我可以盯着路标，一次讲完一个完整意思。中间气口不对、表述绕了、事实说错，就只把这一小段重新说一次。自然的停顿和轻微自我修正不一定都要删，因为那些可能恰恰是人在思考的痕迹。

最后，再把原视频、重录片段和论述路标交给 Codex，让它调用剪辑工具处理废片、长空白和重复 take，按逻辑顺序拼接，输出初剪和剪辑清单。

目前我还不能说 Codex 一定能“剪得很好”。这只是我今天准备验证的假设。真正完成一次素材导入、自动剪辑和人工验收以后，才能判断它是否可靠。

我的当前方法可以概括成：

自由口述 → 语音转文字 → Hermes 整理主线 → 生成详细论述路标 → 看路标分段重录 → Codex 技术剪辑 → 本人验收

今天的事实、假设和判断如下。

事实：过去照着 AI 完整文案录制时，我有明显的念稿感。今天我已经尝试用自己的原话先说，再让 Hermes 整理结构；我也明确要求它不要提供固定台词，而是增加逻辑节点。

假设：不用逐字稿、改看论述路标，能够降低 AI 味；分段录制能减少长段表达压力；Codex 能把多段 take 剪成自然成片。

当前判断：AI 不应该在人开口之前，先决定他要说的每一句话。它更适合在人已经表达之后整理结构，在人重新录完之后执行技术剪辑。

最强的反对意见是：没有逐字稿可能让表达变散，遗漏关键数字和事实，后期剪辑也可能更费时间。

我的回应是：不是完全无稿，而是从“句子级控制”改成“逻辑节点级控制”。数字、来源和不能说错的边界仍然单独做成事实卡，但不把整段话固定下来。

什么会让我改变判断：我会用真实口播做一次验证。如果路标版在自然度、逻辑完整、录制耗时和剪辑耗时上并没有改善，就调整大纲粒度，或者改成“关键句固定、其余自由表达”的混合方式。

我今天最重要的发现是：

人味不一定要在 AI 写完之后再想办法加回去。更好的办法，可能是一开始就不要把自己的表达权交出去。

# 2026-09-12

HermesCN 残酷共学第三期｜Day 3 打卡

Hermes 解决不了自己的问题，我是不是该直接换成 Codex？

今天我冒出了一个有点危险、但确实值得认真想的问题：我在使用 Hermes 的过程中遇到过不少问题，有些问题我直接交给 Hermes，它并没有很好地解决；但当我把同一个问题交给 Codex，让它进入代码和运行环境排查时，往往能够继续往下推进。

那我还有没有必要使用 Hermes？是不是干脆全部转到 Codex 更省事？

我现在不想马上回答“是”或者“不是”。Day 3 的任务正好是研究和验证观点，所以我先把事实、感受和推测分开。

一、目前能够确认的事实

今天我推进了一条团队录音处理流程：群聊里的录音进入飞书妙记，获取带说话人和时间戳的逐字稿，再进行分段总结、生成文档并准备进入 WeKnora。

三段录音已经完成上传和转写，合计约 17.6 万字符；脚本加入了断点续跑和重复任务复用，团队网关也已经重启。这里大量具体的代码检查、脚本修改和故障排查工作是由 Codex 完成的。

但截至今天 22:00，分段总结还没有全部结束，最终文档发布和 WeKnora 入库也没有完成验收。其中一个总结步骤还出现过模型结果不可用。因此，我不能把这件事写成“Codex 已经把整条流程完美跑通”。

今天稍后，我又准备把已有的 Fun-ASR 多人录音转写流程整理成 Codex 可以长期复用的 Skill。这个动作本身也反映了我的倾向：当任务涉及代码、脚本、参数、失败恢复和测试时，我现在更自然地想到 Codex。

二、我的真实观察

这段时间给我的感受是：Hermes 可以和我持续对话、记录背景、运行定时任务、连接消息平台，也能够调工具执行工作；但一旦问题发生在 Hermes 自己的代码、配置或运行链路内部，让它“自己修自己”时，排查过程有时不够稳定。

Codex 的位置不一样。它更像一个直接进入工程现场的人：读代码、追调用链、改文件、运行测试、看失败，再继续修。至少在我最近遇到的几个工程问题中，这种工作方式更容易把问题推进到可验证结果。

这里需要强调：这是我基于近期使用形成的观察，不是对两个产品完整能力的普遍结论。

三、我目前的假设

假设一：当任务的核心是修改代码、调试脚本、分析日志和执行测试时，Codex 可能比 Hermes 更适合作为主工具。

假设二：当任务需要长期记忆、Telegram 或飞书入口、跨会话协作、定时执行以及不同工具编排时，Hermes 仍然有独立价值。

假设三：问题可能不是“二选一”，而是角色划分错了。Hermes 可以负责接收需求、维护上下文和组织工作；遇到深度工程问题时，再把任务交给 Codex。也就是：Hermes 像工作入口和调度层，Codex 像进入代码现场的工程执行者。

四、对这个判断最有力的反对意见

如果一个工具频繁需要另一个工具来修，那么保留前一个工具是否只是在增加系统复杂度？

这是我现在不能回避的问题。多一个平台意味着多一套配置、多一种故障来源，也意味着我要判断什么时候切换工具。如果 Codex 能够覆盖我的大多数真实工作，并且整体摩擦更低，那么继续保留 Hermes 就不能只靠“它什么都能做”来证明价值。

但反方向也成立：修理一台机器的工具，不一定适合代替机器本身。Codex 能修 Hermes 的代码，不自动等于它已经替代了 Hermes 在消息入口、持续记忆、定时任务和多平台协作中的作用。

五、我的当前判断

我暂时不会直接放弃 Hermes。

更准确的判断是：我需要停止把 Hermes 和 Codex 当成两个功能完全重叠的聊天工具，而要用真实任务测出它们各自应该站在哪一层。

今天的证据更支持“Codex 适合深度工程修复”，但还不足以支持“Codex 可以全面替代 Hermes”。同样，Hermes 有很多功能也不等于这些功能对我真的有价值；价值必须由我日常是否持续使用、是否减少切换、是否提高交付成功率来证明。

六、接下来怎样验证

我准备选择五类真实任务做对照：

1．长对话和个人背景延续；
2．内容创作中的采访、素材整理和版本保存；
3．定时任务与消息平台触达；
4．涉及多个工具的长流程执行；
5．代码修改、故障排查和测试。

每类任务记录：是否完成、用了多少轮提示、人工介入多少次、实际耗时、是否产生副作用、失败后能否恢复。

如果 Codex 在前四类任务中也能以更低摩擦稳定完成，我会认真考虑减少甚至放弃 Hermes。如果 Hermes 作为长期入口和调度层能够明显减少上下文丢失，并让 Codex 的工程能力更容易被调用，那么更合理的方案可能是组合，而不是替代。

今天我的观点变化是：

一开始的问题是“要不要放弃 Hermes”。现在我觉得真正需要回答的是：“我的工作里，哪些任务应该由 Hermes 负责，哪些任务应该一开始就直接交给 Codex？”

在做完对照实验之前，二选一只是情绪判断；找到任务边界，才可能得到能长期使用的答案。
